## New owner operations

- `/admin` and `/api/admin/*` check the persisted owner role on every request; `/me` exposes `is_owner`. Friends cannot reach these APIs. User, session, invite and feedback lists are paginated. Friends' AI/sharing permissions and access can be revoked; sessions and unused invites can be revoked.
- Owner roles and owner sessions are deliberately immutable through this dashboard. Allowing the sole owner to demote/revoke themselves risks locking out administration. Creating/transferring owners remains an operator/bootstrap action; roles are visible but cannot be promoted through the browser.
- Real bounded resource samples expose measurement scope, PostgreSQL connections and Celery availability. The log viewer stores safe operational event codes, not unrestricted raw exception bodies containing health data or credentials. It is a capped Redis buffer rather than permanent host-wide log storage, and Redis outages can lose those events.
- Feedback commits with its durable notification outbox before a bounded immediate Telegram attempt. Retries run through Beat; admin displays pending/delivered state. API/worker critical events, final connector failures, redeemed invites and daily summaries also notify the configured owner. Delivery is at-least-once and can duplicate after a crash. No inbound/user chat bot was restored.
- Remembered logins have a rolling 30-day expiry, renewed at most daily, with a 90-day absolute cap. Unchecked logins use a browser-session cookie. Existing remembered rows retain their original absolute cap. Disabled users cannot log in or resolve old sessions.
- Selected-table JSON exports now include the requesting account's feedback. This is not whole-account deletion or a complete legal access-response workflow.

## Historical feature repair

Migration 0016 adds provenance without changing raw observations, historical decisions or expensive user histories during deployment. Newly recomputed days use the corrected method. Previously computed historical load requires a chosen account/date-range repair; it does not silently repair itself on upgrade. On the home server, after taking the normal backup and installing the updated image, use the same Compose overrides as the deployment:

```sh
docker compose --env-file .env -f infra/docker-compose.yml exec -T api \
  python -m tools.recompute_features --user-id 1 --start 2026-09-01 --end 2026-10-07
```

Replace the ID and dates with the account and period requiring repair. Each invocation accepts at most 366 dates and reads preceding data needed for each rolling window. The command changes derived features only, preserving original observations and versioned decisions. An automatic unbounded backfill during migrations was omitted because it would couple deployment downtime and worker/database load to private history size; the home database and required date range were unavailable for safe execution here.
