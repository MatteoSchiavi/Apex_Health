# Owner administration and operational notifications

The `/admin` page uses authenticated `/api/admin/*` APIs. Every admin API checks the database credential role `owner`; friends receive 403 and missing sessions receive 401. Owner permissions and owner sessions cannot be revoked here. Roles cannot be changed through these APIs. Disabling a friend deletes their sessions and blocks further authentication. Account, session, invite and feedback lists are paginated (maximum 100 rows per page). Invite codes are returned only on creation by the new admin APIs; the existing owner settings API retains its previous behavior.

Feedback is stored in PostgreSQL table `feedbacks`. Any authenticated account may submit five messages per hour, up to 2,000 characters each. Page URLs retain only a sanitized route; queries, fragments, origins and invite path codes are removed. Obvious credentials in message text are redacted. Avoid entering private medical records or credentials into feedback. The owner feedback list shows notification delivery status independently from successful database storage.

## Optional owner Telegram notifications

Create a dedicated bot through Telegram BotFather and enter its token securely into environment settings as `OWNER_TELEGRAM_BOT_TOKEN`. Start a conversation with the bot using the owner's intended private account and configure its numeric chat ID as `OWNER_TELEGRAM_CHAT_ID`. Use a dedicated owner chat, not a shared health discussion group. Restart API and Celery processes after configuration changes. Run the owner notification test from `/admin`; its status shows whether settings are present and whether messages are pending or retrying. No live delivery is claimed until configured credentials have been tested.

This bot only sends outbound operational messages. There is no Telegram chat bot, polling process, webhook, inbound commands or Telegram SDK. Telegram notifications cover feedback, invite redemption, critical connector failures, critical API/worker events, and an 08:00 UTC daily operational summary containing measured CPU/RAM/disk, PostgreSQL connection counts and responding Celery worker counts with their measurement scopes. They do not include health records, tokens, invite codes, raw exception messages, request headers or connector response bodies. Feedback messages contain user-submitted feedback, the submitting account’s name/email and numeric ID, submission timestamp and sanitized page route. This feedback is sent to the owner’s configured Telegram chat, an external service; the feedback form explains that destination before submission.

PostgreSQL `owner_notifications` is a durable outbox. Feedback and its notification commit atomically before delivery is attempted. Immediate feedback/invite requests have a maximum five-second Telegram request timeout (two seconds to connect). Beat retries each minute, at most 20 messages per batch, with per-message exponential delay capped at 24 hours. Delivered operational outbox rows older than 30 days are removed; feedback-linked delivery history and undelivered messages are retained. Delivery uses at-least-once semantics: a process crash after Telegram accepts a message but before the database commit can duplicate that message.

## Monitoring scope and operational logs

CPU utilization is measured over a 100 ms sample of host-kernel `/proc/stat`; load and logical processor counts also describe the kernel visible to the process. Memory uses cgroup memory limits and usage when those limits constrain the container, otherwise `/proc/meminfo` describes host-kernel memory. Disk reports the root filesystem visible to the process. Each metric declares its scope. PostgreSQL connections come from `pg_stat_activity`; worker availability uses a bounded Celery control ping. Unavailable services are reported as unavailable. No Docker socket or host shell access is required.

API and Celery workers share a Redis log buffer capped at 1,000 events with seven-day inactivity expiry. The owner may retrieve at most 200 rows and filter severity/source. Only generated event codes, static logger identifiers, severity and timestamps are retained; arbitrary log text, exceptions, health payloads and secrets are omitted. Critical events additionally enter a bounded Redis queue; the minute dispatcher transfers them to the durable PostgreSQL outbox and deduplicates source/event alerts per UTC hour. A Redis outage can lose operational log events; feedback and invite notifications remain durable in PostgreSQL. Celery Beat and workers must run for retries, critical-event dispatch and daily summaries.
