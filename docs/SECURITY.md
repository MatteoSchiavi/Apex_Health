# Security & Encryption Posture — the owner's key story

> Owner requirement: "While the project is private (just me and my friends),
> I would prefer to have data still encrypted, obviously, but I want to have
> the encryption key so I can fix bugs and things like that."
>
> Translation: encryption must be real, but never owner-hostile. There is no
> user-held per-friend key (friends are not vendors); there are exactly two
> secrets, both generated and held by YOU, and any debugging session can be
> handed both. This document is the complete map: what is encrypted, with
> what key, where keys live, and what is deliberately plaintext.

## 1. The two keys you hold

| Key | Env var | Protects | Generated by |
|---|---|---|---|
| **Column-encryption key** | `ENCRYPTION_KEY` | Device OAuth tokens, any stored secrets | You — `openssl rand -base64 32` |
| **Backup key** | `BACKUP_ENCRYPTION_KEY` | The nightly `.sql.gz.enc` artifacts (on-disk + B2 offsite) | You — same command |
| Disk volume key | LUKS passphrase/keyfile (see §4) | Every byte on the homeserver disk, DB volume included | You — at Linux install time |

There is no other key. If you paste `ENCRYPTION_KEY` + the disk key into a
debug session, everything the app can see, the session can see — exactly the
"fix bugs" property you asked for.

## 2. Layer-by-layer: what is encrypted, where

### 2.1 In transit

* **Cloudflare Tunnel (recommended)** or **Tailscale serve/funnel**: TLS from
  the friend's browser to the edge, then an encrypted tunnel to the homeserver.
  The app never sees plaintext credentials on a public hop.
* On the LAN: HTTP is possible (set `COOKIE_SECURE=false`) — acceptable only
  because the hop is inside your network. The moment anything leaves the house,
  TLS in front is **mandatory** (INSTALL §9a).
* Session cookies: `HttpOnly` (invisible to JS), `SameSite=Lax`, `Secure`
  (when `COOKIE_SECURE=true`), plus a CSRF token header on every unsafe
  method (`X-CSRF-Token`, §22.3) — CSRF cannot ride someone else's cookie.

### 2.2 In the database (column-level)

Encrypted with Fernet (AES-128-CBC + HMAC, `cryptography` library) under
`ENCRYPTION_KEY`:

* **Every device token** — Garmin session tokens, Whoop/Strava/Oura/COROS
  access+refresh pairs (`integrations.credentials_encrypted`). A DB leak alone
  yields no usable device credentials.
* Lab values, journal entries and other secrets-classified columns use the
  same `app/core/security.py` helpers (`encrypt_secret`/`decrypt_secret`).

Hashed, never recoverable: passwords (**argon2id**), API-session ids, invite
codes are stored plaintext *by design* — a code is a capability token that the
owner hands to one friend (§6.4); treat a leaked code like a leaked password
(revoke it in Settings → Invites).

### 2.3 The bulk-data decision (read this, it is the honest part)

Hypertables (`biometrics`, `activity_streams`, sleep, stress timelines) and
activity/feature rows are **plaintext inside the DB volume**. This is
deliberate, not an oversight:

* Row-wise application encryption would defeat TimescaleDB compression
  (random ciphertext does not compress), multiply query latency ~100×, and
  break every range-scan the feature engine and AI context builder depend on.
* The SAME protection at ~zero cost is **full-disk encryption (LUKS2/dm-crypt)
  on the homeserver**: every byte on disk — DB, raw payloads, logs, the
  encrypted backups — is ciphertext at rest with a key only you hold.
* Threat model honestly covered by the combination: someone steals the disk
  or an offsite copy → LUKS + backup encryption stop them. Someone gets your
  app account → that is what the session/CSRF/role layer is for. Someone
  steals the whole running server *with keys loaded* → no encryption scheme
  helps (true for every hosted service on earth).

### 2.4 Backups

Nightly 02:00 UTC: `pg_dump → gzip → Fernet-encrypt (BACKUP_ENCRYPTION_KEY) →
./backups bind-mount → optional B2 offsite upload` (§22.7). Restores are a
documented one-command drill (`tools/restore_backup.py`, `restore_drill.py`).
An artifact without the key is noise — including the copies sitting on
Backblaze.

### 2.5 The browser side

* No tokens in localStorage, ever (STACK.md §2.5). The session is a cookie.
* AI conversations persist **server-side** (resumable from any device) and the
  UI additionally mirrors the active conversation id + draft in localStorage —
  the only client-side data, and it is just "where you were".
* Language/theme live on the account, so nothing sensitive is needed for the
  first paint.

## 3. Application-layer guards (already enforced + tested)

* Multi-user isolation is exercised by `tests/test_multiuser_isolation.py`:
  a friend fetching another user's row gets 404, and the SPA fallback can
  never mask an API path with HTML (reserved-API-prefix rule in `main.py`).
* Role model: owner vs friend; invite-only onboarding; owner-only invite mint
  + AI-tier changes (§15/§18).
* AI budget valve per friend (`ai_access_tier`), fail-closed routing.
* Rate limits on auth + AI endpoints (Redis counters).
* The Docker image runs as non-root; containers have memory caps; the bot has
  no inbound port (long polling).

## 4. Turning on LUKS on the homeserver (one-time, 15 minutes)

1. Install the Linux distro with "use entire disk + encryption" (every major
   installer supports it), or for an existing box:
   `cryptsetup luksFormat /dev/sdX && cryptsetup open /dev/sdX crypt && mkfs…`.
2. Put a keyfile on a USB stick or use a strong passphrase; you hold it.
3. `docker compose` volumes live on the encrypted filesystem — done. There is
   nothing app-side to configure: the DB never knows.
4. Verify: `lsblk -o NAME,FSTYPE,MOUNTPOINT` should show your DB volume under
   a `/dev/mapper/…` parent.

## 5. Incident playbook (short, because you hold the keys)

* **Leaked invite code** → Settings → Invites → revoke. Codes are single-use
  anyway.
* **Suspected `ENCRYPTION_KEY` leak** → generate a new key, re-save each
  integration (connect flow re-encrypts with the new key at next connect),
  restart. Old rows decrypt only with the old key, so rotate by re-connecting
  devices, not by batch rewrite.
* **Suspected backup leak** → rotate `BACKUP_ENCRYPTION_KEY`; past artifacts
  stay safe under the old key, future ones use the new.
* **Friend leaves the circle** → delete the account (owner action in DB today;
  settings UI row is a backlog item) — their rows cascade.
* **Lost disk key** → data is unrecoverable by design; that is the deal.
