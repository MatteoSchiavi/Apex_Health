# Product requirements completeness audit

This records the historical baseline before follow-up implementation. See [REQUIREMENTS_GAP_CLOSURE.md](REQUIREMENTS_GAP_CLOSURE.md) for the subsequent changes and remaining evidence limits.

Audited repository revision: `14dece1b0be86e0b8d75fc0d8cc3b52e87fe8b8d`.
Scope: the pasted **PRODUCT RELIABILITY, UX RECOVERY & UNIFIED MULTISPORT EXPANSION** directive, sections 1–30, and its subagent execution directive. This is a source/evidence review, not a production acceptance test or review of unrelated earlier specifications.

## Verdict

**The entire specification is not complete.** Core reliability, reviewed importing, planning, structured workouts, sport overviews, feedback, equipment management and private sharing are implemented. Several requested analytical and educational capabilities remain partial or explicitly unsupported. Production-specific acceptance remains unverified. The earlier delivery summary must not be interpreted as satisfying every requirement.

“Implemented” below means a concrete implementation with recorded automated regression coverage; it does not certify every production scenario or usability claim. “Partial” identifies a specific missing integration or behavior. Safe refusal to calculate an unsupported metric is correct behavior, but is not implementation of that metric.

## Concrete outstanding work

1. **Implement measured goal progress (§15/19).** `backend/app/services/sport_progress.py:308` always returns `value=None`, even for an event goal. Add typed measurable targets, compatible recorded references, explicit provenance and unavailable states for genuinely insufficient evidence. Do not reinterpret saved weekly baselines as prescriptions.
2. **Make compatible comparison inputs reachable (§15/16/19/21).** `sport_progress.py:244` requires `source_metrics.comparison_context` with route, terrain, indoor/time and effort context, plus outdoor weather. Source searches found readers but no ordinary ingestion producer or editor of that context. Verified climb segments have similarly restrictive input requirements. Add a canonical, provenance-preserving capture/import path and end-to-end tests using realistic imported records; do not infer missing facts merely to fill charts.
3. **Complete workout education (§18).** `services/structured_workouts.py:178` only maps top-level steps. `frontend/src/features/athlete/WorkoutDetail.tsx` does not render education targets. Include nested effort/recovery guidance, prescribed intensity, and workout-specific mistakes and conservative alternatives without inventing zones or medical claims.
4. **Represent FTP source and methodology (§16).** `schemas/athlete.py` only supports watts/date/confirmation. `sport_progress.py::ftp_assertion_history` accepts `user_confirmed`, and the current FTP is labeled manually confirmed. Add distinct manual/import/test/estimate provenance and test-protocol metadata; confirmation alone must not imply a validated test.
5. **Implement or explicitly defer automatic interval identification (§15).** It is currently an `unsupported_model` result, not an implemented detector. Require conservative segmentation, confidence/eligibility and irregular/missing-stream tests. Keep grade-adjusted pace unavailable until a defensible model exists.
6. **Add conservative equipment comparisons (§22).** `api/gear.py:156` and `GearHistory.tsx` expose usage, activities and services, without analytical historical performance comparisons. Only compare compatible sessions and disclose confounding; no causal equipment claims.
7. **Connect existing strength analytics to goals (§19).** `services/analytics.py` already supplies volume/Epley estimates through the Lab `gym_progression` recipe. Do not duplicate that engine. Add comparable-exercise, goal-linked explanations where evidence supports them.

## Actual verification evidence

GitHub Actions run [38246044427](https://github.com/MatteoSchiavi/Apex_Health/actions/runs/38246044427) was rechecked during this audit. Its head matches the audited revision; all five jobs succeeded: updater, frontend, agent-evals, pytest and backend-release.

Recorded final results: **1,230 backend tests passed, 1 skipped; 180 browser tests passed, 1 skipped; 26 Coach evaluations passed; 81 updater/Telegram tests passed; 5 PWA tests passed.** These are separate gates, not a count of specification requirements satisfied. Backend-release also exercised image build, migration/boot, worker restart, encrypted backup/restore and failed-restore atomicity. This audit used read-only source inspection and CI metadata; it did not rerun destructive backend fixtures or alter a service.

Live verification remains required for the production reverse proxy/session persistence, real Garmin state transitions and notification delivery, and the host's installed updater/controller plus actual image/schema recovery. Publishing the application image does not install host scripts. Follow `AUTO_UPDATES.md` and `TELEGRAM_CONTROL.md`; this audit neither deploys nor resumes automation.

The subagent directive was followed with one bounded read-only training/analytics specialist; the coordinator handled requirement reconciliation, CI and final conclusions. Findings were reused rather than commissioning overlapping repository-wide audits.
